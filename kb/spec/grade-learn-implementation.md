# E7a: Conservative measured learning

Implement after reviewed C2. The observation/replay semantics in learning-context.md are authoritative over the original E7 prompt. No wiring or simulator work in this slice.

## Grade
- Parse boundary inputs with existing Zod schemas, then validate actual calendar dates and safe integer cents used in arithmetic. Reject duplicate bank transaction IDs rather than counting one record twice. Validate forecast weeks are contiguous Mondays starting at weekStarts(forecastAsOf, ...), and opening/closing/inflow/outflow are internally consistent. A forecast is evidence, not an arbitrary list of balances.
- Follow the completed-week and pre-Monday-gap semantics in learning-context.md. Exclude transactions on the origin date because opening cash already includes them. Missing context or no completed forecast week is an explicit insufficient-observation error. Preserve context-free call compatibility without pretending it is executable.
- Use exact rational arithmetic for error means, strict >3% miss detection, and model comparison; reduce fractions to bound growth. Convert only the final percentage to a number. Do not round cents through floating-point ratios. The denominator is max(abs(actual closing), 1 cent), including negative cash.
- Every miss identifies its week and observed discrepancy. Cite relevant bank transaction IDs as observations, never as proof of which invoice caused the error. A quiet week may have a miss with no transaction to cite. Use factual source/ref/note fields and no fabricated transaction or causal join.

## Candidate policy
- Validate current snapshot/model and authoritative examples. Current paid/card dates after snapshot.asOf are ignored as unobservable; replay origins with such contamination are rejected by C2. Validate same company and example cutoff <= current snapshot.asOf. Reject duplicate record identities used for learning. Do not import the simulator or answer key.
- Customer delay: require at least 3 unique paid invoices for the customer with paid <= current cutoff and valid issued <= paid, due dates. Delay is signed whole calendar days (early payments stay negative). Mean is the arithmetic mean of day counts; p90 is nearest-rank ceil(0.9*n), sorted ascending. Keep unsupported existing customer estimates unchanged. Record sample count and source invoice IDs. This is observed payment timing, not a bank-settlement proof.
- Recurring cards: conservative v1, require at least 3 unique observed records for the exact nonempty merchant, same positive integer amount, strictly increasing dates and identical positive integer gaps. Skip merchants with same-date duplicates, variable amount/gap, or a same-name bill vendor (case/whitespace normalized), because we cannot prove those are separate obligations. Match existing recurringSpend by exact merchant label; replace only a unique match, skip ambiguous duplicate labels, otherwise add one. Preserve unrelated entries and order; append new merchants in stable lexical order. Do not change the existing forecast anchor at asOf + everyDays; state that limitation in learned rule text.
- Build one deterministic candidate from supported observations. Do not invent churn probabilities or signing dates. No supported parameter change means return the original model unchanged.

## Replay acceptance and rules
- No context or empty examples returns the original model without adding rules/version. With context, stored history Forecast[] is ignored for replay; it lacks the required origin inputs. Replay both current and candidate models using forecast(example.snapshot, model, []). Only completed example-weeks count, with equal per-week weight across examples. Skip examples with no completed weeks, but reject malformed contexts instead of silently ignoring them.
- Accept the entire candidate only on strict exact mean-error reduction over nonempty evidence. Ties and regressions return the original model object/data unchanged. Do not use rounded displayed percentages to decide. Version increments exactly once on acceptance, never on repeat learning with identical inputs. Preserve existing approved rules; add factual rules only for parameters that changed in an accepted candidate. Stable rule IDs should avoid collisions with unrelated rules and retain factual evidence.
- Each new rule records the measured overall errorBefore/errorAfter and calls the result retrospective fit. Do not imply per-rule causal attribution or held-out predictive gain. All money remains computed by the engine.

## Verification
- Hand-computed examples: origin Friday with weekend deposit, origin Monday, exact Sunday completion, partial week, 3% boundary and just over, zero/negative actual balances, duplicate transactions and bad week alignment. Inputs remain unmutated.
- Learning: real 3-invoice delay improvement, nearest-rank p90, unsupported two-sample customer, future observations excluded, exact recurring pattern versus variable/duplicate/bill-overlap exclusions; same origins under both models; older supplied history cannot bias comparison; no context/evidence, tie, regression, second-run stability, multi-example weighting, cross-company/future cutoffs and contaminated origins rejected.
- Write failing tests before implementation. Run full check, record exact results and limitations in the card, commit, then stop for independent review.
