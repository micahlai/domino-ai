- Watch out:
  - **Codegen:** `convex codegen` needs `CONVEX_DEPLOYMENT` (no offline mode), so `_generated` is untouched. `lib/refs.ts` uses typed `makeFunctionReference("computed:*")` and `("dev/seedComputed:seed")`. Once `convex dev` or `codegen` has run against a deployment, `internal.computed.*` works the same and refs.ts can be dropped.
  - **Deploy and seed (integration owner):** after `convex dev` or a deploy, run `pnpm --filter @domino/web exec convex run dev/seedComputed:seed`. It returns `{ companyId, created }`, is create-once (marker log `computed.seed`) and never reads or changes the fixture company. Recompute later with `pnpm --filter @domino/web exec convex run engine:recompute '{"companyId":"<id>"}'`. The UI `computeActions` flags still need turning on (UI owner).
  - **IDs:** everything is scoped `c_<companyId>_<asOf>_base` or `..._event_<sorted, encodeURIComponent risk IDs joined by ",">`. Fix branches use the engine's `<parent>__<fixId>`. Demo fix IDs are `c_<companyId>_demo_fix_*`. Event IDs contain commas, so a future `/branch/[branchId]` route must URL-encode them. Risk IDs are the engine's own (for example `risk_late_inv_acme_2027`).
  - **Proposals:** the demo proposals come from the fixture change instructions only. They are labelled "Demo proposal:", their evidence says they are not AI output, and the engine computes their gains. Early payment targets the scanned risk that is exactly one `delay_invoice` on that invoice; the hiring delay is global (`[]`). There is no proposal table. A rerun reuses the candidates saved on the company's computed branches, deduplicated by ID and applied in the order recorded by the `engine.proposal-order` log entry, with new explicit IDs appended in caller order (I2-r1; the original ID sort reordered caller proposals). A proposal that is useful nowhere is not kept.
  - **Rank order:** fix rows are written in rank order and rewritten only when something changes. `forBranch` returns computed rows in index order (`_creationTime`). This assumes Convex gives increasing creation times within one mutation (convex-test does); worth checking on a real deployment.
  - **Fixed snapshot:** a decided fix branch, its ancestors and the candidate it was decided on must recompute identically, or the run is refused with `DECIDED_CHANGED` and nothing is written. Undecided results update in place, and stale undecided computed branches are deleted. Risks and reports from older `asOf` dates are left alone; the queries already read the latest. A new snapshot date makes every older decided branch stale, so it is refused: multi-snapshot handling is still needed before `week.advance`.
  - **Refusals:** recompute refuses companies with non-computed (fixture or legacy) branches, deals with no invoice link or kind, and pay_by_date rules with no bill (`LEGACY_DATA`). It also refuses a missing snapshot or model (`MISSING_INPUT`) and engine errors (`ENGINE_REJECTED`). `simulateFix` refuses fixture futures, stale futures (since I2-r1: any root-to-parent branch, the parent's candidate or the stored risks differ from a fresh run), cross-company ancestors or candidates, cycles and missing ancestors.
  - **addEvent:** it must match exactly one current risk by exact ordered changes, with the label used only to break ties (`EVENT_NOT_FOUND` / `EVENT_AMBIGUOUS`). It keeps that risk's ID and probability, and returns `{ riskId, branchId }`. The single-risk event branch always exists. Arbitrary custom events need a later contract decision.
  - **Audit log:** a run that writes nothing adds no log entry.
  - **Follow-ups (not built):** connectors, agents, `week.advance`, legacy fixture backfill, and production access control.
