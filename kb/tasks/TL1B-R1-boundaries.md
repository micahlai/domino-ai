# TL1B-R1: reject unsafe or unsupported financial inputs

- **Goal:** No saved baseline silently loses money precision or ignores forward financial semantics.
- **Folder:** `apps/web/convex/timeline` only; Result section below.
- **Contracts used:** Snapshot/CompanyModel/Forecast/WeeklySeedV1; frozen schemas unchanged.
- **Done when:** Tests reject aggregate overflow including unsafe intermediate sums; reject unsupported forward fields before engine/save; full stored row UTF-8 bytes are bounded including generated evidence; old fixture flow and check/Convex typecheck pass.
- **Notes:** Independent scratch probes /tmp/tl1-audit/audit.test.ts. 64 recurring costs of 2**49 cents everyDays1 save 51 unsafe numeric forecast fields. Rehashed writtenOff invoice saves unchanged $240k inflow; collection/agreedPayOn/billingPlans/pendingPayouts ignored. Fail closed on these plus paidAmount and any other accepted financial extension unused by current engine. Empty optional arrays may be harmless if explicit.
- **Size reproduction:** Minimal schema-valid seed has two card txns (Sep15=100, Oct15=1000 cents); Oct merchant is 550000 ASCII characters. Seed canonical text 550673 chars passes, but pastEvents repeats merchant into evidence and full saved row exceeds 1.1 MB. Reject by total encoded row size before insert, not seed chars alone.
- **Approach:** Conservative BigInt bound on cumulative/absolute cash movements including repetitions/history or other correct pre-computation rejection; do not only check final outputs where unsafe intermediates could cancel. No shared engine changes or silent field deletion. Clear error naming unsupported field. Preserve interface and immutable retries.

## Result
- Done: Three pre-insert guards in `save`, interface unchanged. (1) `checkMoneyBound`: BigInt sum of absolute cash on hand, restricted cash, every invoice/bill/payroll/deal/bank/card amount, each recurring spend times its maximum repetitions in the 98-day horizon (`floor(98/everyDays)+1`), and min-cash limits; over `Number.MAX_SAFE_INTEGER` -> `UNSAFE_MONEY` before the engine runs. Every engine balance, weekly flow, history balance, usable cash and shortfall is a signed subset sum of these, so cancelling intermediates cannot hide lost precision. (2) `checkSupportedFields` (in seed parse): non-empty `billingPlans`/`pendingPayouts`, invoice `writtenOff`/`collection`/`paidAmount`/`billingPlanId`, bill `agreedPayOn` -> `UNSUPPORTED_INPUT` naming the record and field; explicit empty arrays accepted. Remaining C3 additions checked against `packages/engine/src/schedule.ts`: deal `invoiceId` is read by the engine; deal `kind` is a label with no cash effect. (3) `checkRowSize`: UTF-8 bytes of canonical JSON of the complete row (seed text plus generated forecast/dominoes/history/pastEvents evidence) over 900,000 -> `TOO_LARGE` before insert. 14 new convex-test cases: 64 and 2 daily max spends, one spend every 98 days accepted vs daily rejected, net-zero history transfers with unsafe partial sums, min-cash limits in bound, each of six forward fields (engine never called, nothing written), empty forward arrays, 550,000-char ASCII and 320,000-char multi-byte merchant rows rejected, small version saved. Mutation check: disabling the three guards fails 12 tests. Original Kestrel path tests unchanged and passing. `pnpm check` (web 506; 1,649 total; lint 315 files), separate `tsc --noEmit -p convex`, lane inventory (18, 0 harness) pass.
- What changed (files): `apps/web/convex/timeline/baselines.ts`, `apps/web/convex/timeline/baselines.test.ts`, this Result.
- Watch out: The money bound is deliberately conservative (it counts paid invoices, unsigned deals and card spend the forecast may skip), so a seed near 2^53 total absolute cents is rejected even if its real sums are smaller; Kestrel is far below. Row size uses canonical JSON bytes, which slightly differ from Convex's internal encoding; the 900,000 margin under 1 MiB covers that. Forward-field rejection is fail-closed until engine support lands through the shared checkpoint. Not run against a live backend; lead deploys and verifies.
